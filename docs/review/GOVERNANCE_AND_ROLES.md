# 评审治理、角色与回避规则

> 状态：公开讨论稿  
> 版本：v0.2-draft  
> 本文件补充 [GOVERNANCE.md](../../GOVERNANCE.md)，不虚构当前已经存在的委员会。

---

## 一、当前治理事实

按照现有治理文件，初创阶段由项目发起人承担主要维护和核心文件最终审阅责任。公开评审不会自动改变 GitHub 仓库权限，也不会把任何被邀请者包装成项目委员。

每轮开始前必须公布实际承担下列角色的人或公开称呼。未填满角色时应披露兼任情况和独立性局限，不得使用“委员会决定”“集体通过”等与事实不符的表述。

---

## 二、角色与权限

| 角色 | 主要职责 | 不得实施的行为 |
| --- | --- | --- |
| 最终决定责任人 | 对原则修订、暂缓或不采纳作出理由化决定；初期通常为发起人 | 不得隐瞒利益冲突、删除合理异议或独自认定自己起草的文本已通过独立评审 |
| 轮次协调人 | 发布公告、控制时间、协调分轨审阅和总结 | 不得擅自改变被评版本或公开授权 |
| 收件记录员 | 生成私密随机回执编号；经授权后另建公开记录编号；维护台账和回执 | 不得把私密编号或身份映射写入公共台账 |
| 身份核验员 | 查看最少核验信息并记录核验结果 | 不得评价观点正确性或传播原始材料 |
| 隐私负责人 | 管理访问、删除、权利请求和事件响应 | 不得将材料用于宣传、画像或招募 |
| 专家意见整理人 | 按专业维度整理意见、证据与冲突 | 不得代替劳动者判断真实劳动处境 |
| 劳动者意见整理人 | 整理可理解性、场景真实性和影响 | 不得把个人经验包装为全体意见 |
| 修订执行人 | 根据决定修改文件并记录差异 | 不得越过公开决定自行改变核心立场 |
| 复核人 | 检查程序、证据遗漏和利益冲突 | 原处理者不得独自复核自己的决定 |

一个人可以兼任协调、记录和修订，但身份核验信息应尽可能与实质意见处理分离。只有一名维护者时，必须在轮次总结中明确“无法实现独立复核”的局限；涉及重大利益冲突的事项应暂缓，直至找到临时独立复核人。

如果最终决定责任人参与了被评条款的起草，其合并权限仍遵循现有 [GOVERNANCE.md](../../GOVERNANCE.md)，但该决定只能标记为“维护者草案决定”。第一轮如要称为“完成双轨流程试评审”，至少还须有一名未参与该条款起草的正式劳动者和一名未参与该条款起草的相关正式专家分别确认：其轨道意见已被准确处理、重大风险没有被忽略；这不表示文本稳定或具有代表性。第二轮及以后适用本文件第六节的更高门槛。两人不能由同一人兼任。

## 四、利益冲突

下列关系应主动声明：

- 对被评文字有直接起草、批准或署名责任；
- 与相关企业、平台、工会、研究机构、政治组织、资助方、商业产品或题目投稿者有管理、所有权、任职、资助、合同、共同署名或其他组织关系；
- 评审结论可能直接影响本人工作、合同、诉讼、项目收益或声誉；
- 与劳动者参与者、提交者、起草者或决定者存在可能影响独立判断的密切关系或直接争议；
- 其他理性旁观者可能认为会影响公正处理的关系。

利益冲突分为：

1. **无已知冲突**：正常参与；
2. **可管理冲突**：公开关系，可提供意见，但不得作为唯一依据；
3. **重大冲突**：可以提交带标签的观点，但应退出该事项的最终决定、身份核验或复核。

观点鲜明、批评项目、公开表达过倾向或持有某种理论立场本身不构成应被排除的利益冲突；应披露和分类的是可能影响处理独立性的事实关系。

## 五、回避程序

1. 参与者或处理者在发现冲突后立即向协调人声明；
2. 协调人记录冲突类别和拟采取的限制，不公开不必要的私人细节；
3. 被质疑者可说明情况，但不能单独决定自己是否回避；
4. 由无冲突的决定责任人或临时复核人确认处理方式；
5. 如无人可以独立处理，该事项标为“暂缓处理—等待独立复核”；
6. 公共决定日志记录回避事实、对程序的影响和替代措施。

## 六、裁决评审组与成熟度门槛

第二轮和第三轮中，拟将实质条款称为“完成双轨评审”或“可作为稳定文本使用”前，应按条款组成五人裁决评审组：

- 两名具有相关经历的正式劳动者；
- 两名相关领域的正式专家；
- 一名无重大冲突的维护者或最终决定责任人。

成员从本轮已公开招募条件的候选池中，按相关性、可用性、覆盖缺口和利益冲突选择，不按是否赞同现稿选择。任何人只能占一个席位；同一机构、资助或直接管理关系下的成员最多两席，且不得包办同一轨道。条款起草人、题目投稿人、直接管理者、直接资助或收益相关者应就该事项回避相应审阅或裁决席位。无法继续参与时，按同一公开条件补位并记录原因，不得临时只寻找支持者。

公开记录可使用不含身份含义的席位编号，并只发布无法反向识别的构成与人数。姓名、单位、个人对应的“已核验轨道”状态和席位关联分别取得授权；不愿公开身份或核验状态不影响其意见有效性，也不得被用来施压公开。无法安全披露细分时，只公开由记录员和复核人确认的聚合构成及这一透明度局限。

裁决评审组不采用简单多数票。两名劳动者和两名专家应分别给出本轨道结论、理由和异议；维护者给出仓库处理决定并回应两个轨道。四名独立轨道评审者均实际完成审阅，且修改、异议、回避和局限已记录时，只能说明“完成双轨评审”，不自动说明文本稳定。

若要进一步标记为“稳定使用（仍可重新评审）”，四名独立轨道评审者必须复看拟生效版本的最终 diff、commit 和 SHA-256，均不得留下尚未回应的事实、基本权利、安全、严重伤害或关键适用范围异议，且两个轨道均确认主要反对意见已被准确处理。对被冻结旧稿完成审阅、但意见合并后的新文本尚待四人复看时，只能标记为“完成双轨评审—可继续修订”。非实质性的文字偏好可以保留并公开；上述实质分歧无法解决时标记为“完成双轨评审—争议未决”。人员或证据不足时标记为“证据不足”，不得用维护者合并行为替代评审结论。

稳定状态只适用于决定记录写明的精确文件版本、commit 和 SHA-256。此后发生任何可能改变含义、适用范围、权利或风险的修改时，新版本先回到“维护者草案”或“待四人确认”，不得自动继承旧版本成熟度；纯格式或链接修正也应说明为什么不影响含义。

裁决评审组形成的是评审结论和建议；GitHub 仓库是否合并仍是单独的维护权限决定。维护者可以依现有治理合并草案，但必须按真实成熟度标记，不得把“已合并”表述为“已通过独立评审”。

第一轮是流程测试，不适用五人组和代表性门槛；如人员不足，只能发布流程试评审结果或维护者草案。后续轮次如果项目规模不足以组成上述小组，应公开能力缺口并保持相应事项未决。

## 七、决定权与“评审通过”表述

初创阶段核心文件是否合并仍依 [GOVERNANCE.md](../../GOVERNANCE.md) 由发起人或未来维护者最终审阅。该权力必须受到公开理由、版本记录、利益冲突回避和复核程序约束。

“有权合并”不等于“独立评审已经完成”。存在以下任一情况时，只能发布维护者草案或暂缓决定：

- 决定人是相关条款的起草人，且没有独立劳动者与独立专家的双轨确认；
- 重大风险尚未完成劳动者和相关专家的分别核查；
- 需要复核但没有任何未参与原处理的人；
- 对外表述所需的评审轨道或公开授权不足。

不同成熟度应使用不同表述：

- **维护者草案**：尚未完成正式专家与劳动者评审；
- **流程试评审版本**：完成第一轮流程测试，但不主张代表性；
- **定向评审修订版**：完成第二轮并披露覆盖范围与缺口；
- **公开征集修订版**：完成第三轮公开征集和理由化处理；
- **持续修订版本**：已发布但仍可重新评审。

不得仅因获得若干赞同、达到多数票或有知名专家参与，就使用“劳动者一致认可”“专家认证”“代表工人阶级”等表述。

## 八、证据与决策记录

每一项评审意见的实质性处理必须在 [DECISION_LOG.md](DECISION_LOG.md) 中说明。涉及核心方向、许可证或治理结构的重大决定，还应同时建立或链接 [docs/decision-records/](../decision-records/) 下的项目级决策记录：前者回答“这条评审意见如何处理”，后者回答“项目为什么作出重大方向决定”，两者通过决定编号、Pull Request 或 commit 相互链接。

- 修改或不修改什么；
- 为什么；
- 依据哪些评审编号、事实与来源；
- 专家意见与劳动者意见分别如何；
- 哪些意见未采纳及原因；
- 有哪些回避、复核或程序局限；
- 尚存什么争议；
- 决定适用于哪个版本。

决定人可以与多数意见不同，但必须说明更高优先级的事实、权利、严重风险或一致性理由。

## 九、参与者行为边界

所有角色均应遵守 [CODE_OF_CONDUCT.md](../../CODE_OF_CONDUCT.md)。不得：

- 要求劳动者公开证明身份；
- 因意见内容决定是否通过身份核验；
- 私下联系、施压或追查匿名提交者；
- 公开未经授权的单位、岗位或联系信息；
- 篡改人数、删除不利意见或把重复提交计算为多人支持；
- 以项目名义承诺资金、岗位、法律结果或组织代表权。

---

## 十、角色变更

角色任免、权限变化和访问权撤销应记录日期与适用轮次。人员退出后应立即撤销非公开材料访问，并由隐私负责人检查其持有的临时副本是否按要求删除。
